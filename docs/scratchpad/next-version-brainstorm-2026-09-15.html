2What The Product Is, Restated

Ledger is repo-native implementation memory. Markdown records under .ledger/ say what changed, why, which files, symbols, docs, decisions, and backlog items are involved, what invariants must survive, what verification proved it, and what to preserve during a merge conflict. Agents are the primary audience. Everything generated is a derived artifact.

Standing constraints any plan must respect: D001 Markdown is the source of truth; D002 .ledger/ is the root; D003 no Dossier coupling in core; D004 Ledger manages a docs lifecycle but is not a docs CMS; and the roadmap's direction of repo-native, no hosted service required, renderer independent, never a generic project management suite.

Strong today

  • A complete record model with validation profiles, baselines, and typed error envelopes shared by CLI and MCP.
  • Git-aware drafting, coverage, docs impact, and CI range checks that are correct in clean pull request checkouts.
  • Token-budgeted packets, weighted search, conflict guidance, and eight read-only MCP tools.
  • Journaled, optimistic, recoverable source mutations.
  • A hardened loopback server, a fail-closed public export profile, and integrity hashing.
  • 36 test files, three-OS CI, a supply-chain audit, and install smoke tests.

Structurally weak, verified in source

  • src/cli.ts is one 1,830-line switch with hand-rolled argument parsing; five workflows have extracted command models.
  • Every command re-parses the whole catalog. No cache, no incremental indexing, no hash short-circuit.
  • ledger serve is static only. No API, no events, no live reload; watch rebuilds everything.
  • MCP is stdio only, with no resources, prompts, output schemas, or structured content.
  • typescript is a devDependency, so installed users silently get regex symbols.
  • The 1,573-line browser runtime is never executed by a test; search scoring is duplicated in Node and browser.
  • The internal reader measured 2,073,552 bytes against a 2,000,000 byte budget in August; never reconciled.
  • Nothing captures a record automatically, and the feedback command has never been used here.
  • Twelve commands and subcommands have no --json envelope.

3The Landscape In September 2026

The roadmap was written before several things changed.

Model Context Protocol

The 2026-07-28 specification made the core stateless over Streamable HTTP, removed the session handshake, added required Mcp-Method and Mcp-Name headers, replaced server-initiated elicitation with multi round-trip requests, promoted long-running work to a Tasks extension, added ttlMs caching on list responses, and shipped MCP Apps as the first official extension. The public roadmap prioritizes local servers speaking Streamable HTTP, progressive discovery of large tool catalogs, and standardized tool results. Ledger's stdio server predates all of this. The TypeScript SDK is at 1.30.0 with Streamable HTTP and an experimental tasks module.

Agent conventions

Agent Skills (SKILL.md under .agents/skills/) are supported by Claude Code, Codex CLI, Cursor, Gemini CLI, and Copilot. AGENTS.md is the accepted place for project instructions. Claude Code exposes 33 lifecycle hook events including SessionStart, PostToolUse, Stop, and PreCompact. Ledger generates none of these; ledger agents prints text to paste.

Competitors

kgai keeps an immutable decision graph the agent captures automatically and syncs without merge conflicts. chamnan commits an architecture index, an impact map, and decision records beside the code. Cognee and Mem0 sell hosted graph or vector memory over MCP. PROJECTMEM proposes an event-sourced local memory and judgment layer. Ledger's edge is that it validates, gates CI, manages docs impact, groups releases, guides conflicts, and budgets tokens. Ledger's gap is that none of its memory is captured automatically, none is reachable without a shell, and none carries proof it is still true.

Runtime

Node 24 ships node:sqlite as a release candidate, native fs.glob, and stable worker threads. Ledger already requires Node 22 or newer.

4Thesis For The Next Version

Move Ledger from a CLI that re-reads Markdown to a local memory engine that agents talk to. Four pillars carry that, plus one hygiene track that comes first.

A

Engine

One operation registry, an incremental cache, shared search, and parser-backed symbols that actually ship.

B

Engine server

A loopback process with a versioned JSON API, an event stream, live reload, and MCP over Streamable HTTP.

C

Capture

Hooks, skills, and authoring commands so records get written by the workflow instead of by memory.

D

Trust

Provenance for the current change, evidence-backed verification, freshness against code, and CI annotations.

E

Reader and publishing

The human surface catches up to the engine.

F

Hygiene

Publish what exists, fix the branch model, and stop advertising what does not exist.

AEngine

Under the hood. Everything else derives from A1 and A2.

A1

Operation registry

Define each operation once: name, description, zod input schema, zod output schema, handler, human formatter. Derive the CLI parser and help, the MCP tool list with output schemas, the HTTP routes, the command reference in docs, and golden contract tests from that one table. This retires the 1,830-line switch and the flag allow-list, and ends the CLI, MCP, library, and browser drift the August audit named. Zod is already a dependency.

A2

Incremental catalog cache

Key each parsed record by content hash and store the normalized document, sections, and derived relationships as a derived artifact under .ledger/cache/. Stat the source tree, re-parse only changed files, rebuild only dependent indexes. Targets for ledger metrics: a warm explain under 50 ms at 1,000 records and under 200 ms at 10,000.

Two backends worth prototyping: a single JSON cache file with no new dependency, and node:sqlite with no new dependency but a Node 24 floor. The cache is disposable and never read as source, so D001 holds.

A3

Search v2

One scoring module shared by Node and the browser, bundled into the reader instead of duplicated. Shard search-index.json by kind and year so the reader loads only the shard the query needs. On the sqlite backend, FTS5 gives ranked search for catalogs that outgrow in-memory scoring.

A4

Typed browser runtime

Move the reader runtime out of template strings into real TypeScript modules with a build step, and run it in a browser test harness. The runtime is 12 percent of the codebase with zero executed coverage.

A5

Symbols that ship

Make typescript an optional peer dependency and report which extractor ran in the draft. Add an extractor registry so Swift, Python, Go, and Rust get at least heading-quality extraction, and document the fallback honestly.

A6

Budgets that tell the truth

Lazy-load the raw source sidecars, recompute the budget, and make doctor fail rather than warn when a profile is over.

BThe Engine Server

The "tiny server with its own API" idea, made concrete. The existing loopback, token, and header hardening applies unchanged.

B1

ledger serve --api

One loopback process that hosts the static reader, a versioned JSON API at /api/v1/ generated from the registry (explain, search, packet, query, conflict, docs impact, validate, doctor, stale, coverage), a server-sent events stream at /events for record changes and rebuild status, and the MCP server at /mcp speaking 2026-07-28 Streamable HTTP with a .well-known server card.

B2

CLI delegation

Write .ledger/daemon.json with the port and token while the server runs. Any CLI command that finds a live server becomes a thin client against the warm cache instead of re-parsing the catalog. The largest single latency win available, and it costs nothing when no server is running.

B3

Live reload

The reader subscribes to /events and re-renders changed records in place. Watch mode becomes incremental by using the A2 cache.

B4

MCP v2

Resources (ledger://entries/0092, ledger://packet/<path>), prompts derived from the ledger agents roles, outputSchema and structuredContent on every tool, multi round-trip confirmation on any tool that writes, the Tasks extension for render and migrate, and ttlMs on list responses. Keep stdio for hosts that need it; both transports share the registry.

B5

Integrations as API clients

A VS Code hover or a browser extension that shows the packet for the file under the cursor is a small client of B1, not a separate product.

CCapture

The competitive gap is that Ledger's memory depends on someone remembering to write it. Fix that at the workflow layer.

C1

ledger hooks install --host claude-code|codex|cursor

Generate host hook configuration. SessionStart injects a budgeted packet for the areas the session is likely to touch. PostToolUse on edit tools records touched paths into a session record. Stop and SessionEnd draft a receipt from the diff plus the touched-path list. PreCompact writes a handoff packet so the next context window starts with the same memory.

C2

ledger skills install

Ship a SKILL.md into .agents/skills/ledger/ with host symlinks, so any skills-aware agent learns when to call explain, packet, conflict, and new without prompt engineering. ledger agents --write maintains a fenced block in AGENTS.md instead of printing text.

C3

Authoring commands

backlog new, decision new, promote <id>, scratch <title>, and release notes, all through the transaction layer, all with --json envelopes, so agents can create every record kind.

C4

ledger ready

A lifecycle-aware gate that distinguishes a structurally valid draft from a record ready to land: no TODO placeholders, verification present, docs impact declared, referenced files exist.

C5

Session and handoff records

A short-lived record kind that captures what an agent session touched and learned, with an expiry, so it is promoted into a change entry or expires instead of rotting as scratch.

DTrust And Provenance

Why a team would rely on the records.

D1

Current-change coverage

Coverage today is satisfied by any historical record that mentions a path. Bind coverage to entries changed in the selected Git range so a pull request must carry its own receipt.

D2

Per-file docs impact

Replace the single boolean with per-file evidence, so one docs touch cannot satisfy an entire change set.

D3

Evidence-backed verification

ledger verify --run executes the commands listed in a record's verification section from an allowlist and writes a derived sidecar with command, exit status, duration, and the commit it ran against. Records gain a "verified at" signal that doctor, the reader, and packets surface, and that stale ages out.

D4

Freshness against code

Extend stale to check every referenced file, symbol, and anchor against the current tree, and flag invariants whose anchors no longer exist. The "withholds stale knowledge" property competitors advertise, computed from records Ledger already has.

D5

Unified retrieval contract

One relationship-aware result model shared by explain, packet, conflict, MCP, and the API, with supersession edges in the graph and traversal into related decisions and backlog items.

D6

First-party GitHub Action

Package the proven ci --base --head logic as a reusable action with annotations on missing coverage, a job summary, and an optional pull request comment.

D7

Release records drive GitHub Releases

release.yml publishes the release record's public notes as the GitHub Release body, so four unpublished tags never happen again.

11Verdict On Every Existing Proposal

Fifty-two recorded proposals have no implementing code and sixteen are partial. Each was weighed against the product goal, the four decisions, and whether a real consumer exists.

Keep as recorded
  • B005 command extraction, absorbed by A1.
  • ledger promote from PRODUCT.md, absorbed by C3.
  • Sharded search indexes (Roadmap Phase 10), absorbed by A3 and E4.
  • Richer graph navigation and PR annotations (Phase 10), now E3 and D6.
  • Reusable GitHub Action (Phase 7), now D6.
  • Evidence references in entries and releases (Phase 9), now D3.
Merge, shape changed
  • Change-set review workbench becomes a context operation and API route, not a UI product.
  • Canonical operation registry is A1 and is now the foundation everything derives from.
  • Write-capable agent lifecycle is B4 plus C3, gated by multi round-trip confirmation rather than a bespoke revision token.
  • Live preview loop is B3. Typed progressive MCP is B4.
  • Self-healing maintenance becomes doctor --fix on top of the A2 cache.
  • Audit findings A, B, E, F become D1, D2, D5.
  • Git merge hook helper folds into C1.
  • search.sqlite as an index is recast as the optional A2 cache backend, never source.
  • VS Code extension prototype becomes an API client under B5.
Drop or defer
  • Go and HTMX mini-app adapters. No consumer exists, and the B1 JSON API serves any language without shipping adapters.
  • Signed records and transparency logs. Nobody is asking for non-repudiation; integrity hashes plus D3 evidence cover the real need. Revisit at 1.0 if a team adopter needs it.
  • Dossier adapter. Out of core by D003; nothing to do until Dossier needs it.
  • Repository federation. Premature before one repository has outside users.
  • .ledger/routing/ directory. docs/llm/ already works; keep one convention.
  • Separate scratch directory. Replaced by C5 records with expiry, which validate and index like everything else.

13Decisions Recorded

Kyle answered the five open questions on 2026-09-15 and asked for the better engineering option regardless of effort. The answers live in decision records D005 and D006 and in docs/ROADMAP.md Phase 11.

  1. Dependency policy. A bundler and a browser test harness are allowed as dev dependencies for A4. The cache sits behind a backend interface: JSON by default on every supported Node line, node:sqlite selected automatically when the runtime exposes it, with FTS for large catalogs. No native addons. typescript becomes an optional peer dependency.
  2. Host priority: Claude Code, then Codex CLI, then Cursor.
  3. Server model: an explicit ledger serve --api that CLI commands use opportunistically through .ledger/daemon.json. No auto-spawned daemon. Deterministic lifecycle, no orphaned processes, and the existing loopback hardening applies unchanged; a SessionStart hook can start it.
  4. Version framing: stay on 0.x with no contract freeze for now.
  5. Drops recorded. Section 11 is recorded in decision D006, and the roadmap now points at this direction as Phase 11.
